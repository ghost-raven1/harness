# Следующий этап: измеряемая работа специалистов

Предложение после 0.6.0; изменение алгоритмов требует отдельного принятия плана.

## Что известно сейчас

В текущем runtime роли берутся из конфигурации, а журнал связывает запросы модели и инструменты с агентом. Расход токенов накапливается на уровне запуска. Проектные проверки дают подтверждённый результат этапа. Стенд 0.6.0 измеряет задержки каталогов при параллельном diff; он не измеряет полезность делегирования и не доказывает, что несколько агентов лучше одного.

Поэтому первым результатом должен стать воспроизводимый отчёт, а не новый диспетчер специалистов.

## Порядок работ

1. В событиях каждого model-запроса сохранять устойчивый ID, роль, длительность, usage и исход. Отдельно учитывать ожидание модели, инструмента, разрешения и дочерних веток. Старые события остаются допустимыми; недостающие времена отмечаются как неизвестные.
2. Построить производный отчёт по дереву задачи: полезная работа, повторы, ожидания и результаты проверок. Не суммировать пересекающиеся интервалы как общее время пользователя. Не приписывать токены одной роли по средней доле.
3. Создать доверенный набор задач в чистых временных папках: независимые файлы, связанный рефакторинг, исправление теста, исследование и задача с конфликтующей областью записи. Для каждой — фиксированные критерии и одинаковые исходные данные.
4. Сравнить три режима: координатор, заданные человеком роли, нынешнее автоматическое делегирование. Использовать закреплённые модель, конфигурацию и версию опыта; не менее трёх повторов каждого случая. Отдельно отметить 429, ошибки провайдера и ожидание человека.
5. Выбрать изменение по результатам: улучшить передачу контекста, ограничить бесполезные повторы либо скорректировать выбор роли. Менять один фактор за раз и повторять тот же контрольный набор.

## Границы

Runtime публикует факты; прикладной модуль строит отчёты через интерфейсы журналов. CLI показывает распределение времени и проверенный результат. Тексты задач и секреты не попадают в сводные метрики. Проекты и обучение не импортируются в runtime.

Права дочерних веток остаются пересечением полномочий родителя. Последовательный диспетчер мутаций сохраняется. Параллельные записи в пересекающиеся области не добавляются без отдельной модели конфликтов. Новых токеновых квот нет.

## Критерии принятия

- Один model-запрос не учитывается дважды после восстановления и повторной обработки событий.
- Время дерева правильно считается при пересечении веток, отмене, ожидании разрешения и handoff.
- Исторические задачи открываются без миграции; отсутствие метрик объясняется.
- Отчёт различает скорость и качество: ускорение с новыми провалами тестов не принимается.
- Выбранное улучшение воспроизводится на целевых задачах и не ухудшает независимый набор.
- Сводные экраны сохраняют действующий бюджет задержки меню; вычисление отчёта не читает все переписки при каждом обновлении.

Результаты измерений и выбранный алгоритм оформляются отдельным предложением перед реализацией изменения маршрутизации.
