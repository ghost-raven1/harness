# Роли, планирование и восстановление

Роли задаются в JSON-файле, указанном в поле `roles` манифеста. Имя роли произвольное: движок не содержит списка обязательных специализаций. Каждая роль получает свой Markdown-промпт, разрешения, файлы памяти и необязательный `modelProfile` из настроенных профилей.

```json
{
  "catalog": {
    "prompt": "prompts/catalog.md",
    "permissions": [{ "tool": "fs.read", "decision": "allow" }],
    "modelProfile": "qwen",
    "memory": []
  }
}
```

Этот пример — одна запись в файле ролей. Роль из `defaultRole` также должна присутствовать в нём. Права всех предшествующих ролей ветки сохраняются при делегировании и передаче работы.

В манифесте `coordination: "auto"` включает выбор маршрута перед новым ходом. Это значение используется и при отсутствии поля. Для ручного управления инструментами агентов можно указать `"manual"`.

При автоматическом выборе модель получает каталог настроенных ролей и один структурированный инструмент `agents.plan`. Возможны три решения:

- `direct`: текущая роль выполняет небольшую задачу или задаёт уточняющий вопрос.
- `parallel`: независимые части передаются подходящим ролям. Команда ограничена `limits.agents`, запросы моделей — `limits.modelConcurrency`.
- `handoff`: текущая ветка переходит к выбранной специализации.

Движок проверяет структуру плана, наличие ролей, пределы и запреты. Проверенный план преобразуется в обычные `agents.delegate` или `agents.handoff`; каждый вызов проходит проверку политики и однократное разрешение человека. Неверный план можно исправить один раз, до любого исполнения. Обычный текст и посторонние вызовы на этапе планирования не исполняются.

Планирование расходует общий предел шагов и учитываемые токены. План и ID подготовленных вызовов сохраняются вместе. При паузе продолжение использует сохранённый план; старые запуски без этого поля сохраняют прежний способ работы. Новые изменения ролей применяются к новым запускам. Активная задача, compaction и handoff используют зафиксированный снимок.

Одна группа содержит независимые подзадачи. Проверка результата, которой нужны уже выполненные изменения, назначается следующим делегированием после получения результатов. Корневая роль собирает незабранные результаты перед итоговым ответом. Количество агентов не означает количество одновременно исполняемых команд: чтения используют общий ограничитель, мутации выполняются последовательно.

`expectedParentRunId` в `harness.run` и локальном `runtime.run` связывает ответ с конкретным предыдущим ходом сессии. Если другое окно уже продолжило беседу, устаревший ответ отклоняется до запуска модели. Повтор ранее принятого запроса с прежним `requestKey` возвращает тот же запуск, даже если история успела продвинуться.

Распределение по ролям улучшает организацию работы, но качество выбора зависит от модели и написанных специализаций. Для узкого вопроса один участник остаётся нормальным результатом планирования. Выбранная причина, делегирование, смена роли и результаты участников доступны в журнале задачи.

## Ограничения провайдера

`retries` в профиле модели задаёт от 0 до 3 повторов после первой попытки. При временной ошибке интервал увеличивается; для `429` учитывается `Retry-After` в секундах или формате HTTP-date. Общее автоматическое ожидание ограничено меньшим из `timeoutMs` и 30 секунд. Если провайдер требует ждать дольше, задача сразу сохраняется на паузе. Исчерпание квоты или баланса не запускает бесполезные повторные попытки.

После исчерпания повторов ограничение провайдера приостанавливает всё дерево задачи. В «Технических подробностях» видны причина и местное время следующей разрешённой попытки, если провайдер его сообщил. Продолжение до этого времени отклоняется без запроса к модели. Позднее пользователь выбирает «Продолжить задачу». Токеновые квоты самого Harness по-прежнему отключены.

Сбор результата ребёнка и отметка «получен родителем» записываются атомарно. Поэтому пауза второго специалиста не теряет готовый результат первого. При восстановлении готовые дети и подтверждённые эффекты не выполняются заново. Неизвестный результат мутации требует прежней проверки человека.

Обучение при таком ограничении сохраняет задание в очереди и ставится на паузу. Его можно продолжить отдельной командой обучения после снятия ограничения. Сбой обучения не меняет результат пользовательской задачи.

Для Codex используются структурированные ошибки установленного app-server. Harness ограничивает собственные повторные обращения и тайм-аут каждого обращения; внутренними HTTP-повторами встроенного провайдера управляет Codex. Текст сообщений модели не используется для распознавания квоты.
