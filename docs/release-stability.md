# Стабилизация релиза

Текущий выпуск — **0.3.1**. Проверка поставки охватывает запуск установленной команды, отмену подготовки и состав передаваемого архива. Команды упаковки создают локальные файлы; публикация, Git-тег и развёртывание выполняются отдельно.

## Изменения в 0.3.1

- Повреждение маркера сборки не запускает повторный `npm ci`, если отдельный маркер установки соответствует lockfile, runtime и платформе. Дерево зависимостей по-прежнему проверяется через `npm ls`; изменение lockfile или удаление обязательного пакета требует установки.
- Отмена и таймаут подготовки останавливают принадлежащее команде дерево процессов. Возврат из команды согласован с завершением остановки, чтобы потомки npm не удерживали временную папку после теста.
- Регрессии проверяют повреждённые маркеры, зависшего потомка и освобождение папки. Таймауты не увеличены. Выпуск не содержит проектного режима.

## Изменения в 0.3.0

- Имена IPC-команд связаны со схемами входа и ответа; произвольный generic ответа удалён из клиентов. Старый конверт протокола 1 совместим, неизвестная версия отклоняется до выполнения.
- Сборка приложения, группы команд и каскадное удаление находятся в `application`. Runtime использует порты чтения, записи, артефактов, вывода и служебных файлов; направления импортов проверяются тестами.
- JSONL версии 1 проверяется потоково. Просмотр не ремонтирует файлы; неизвестная версия и повреждение завершённой записи включают режим диагностики. Конфигурация и версия обучения не мигрируются при чтении.
- Меню использует каталог без переписок. Страницы истории и вывода читаются по разреженным смещениям; исторические снимки ограничены LRU-кэшем 64 МиБ. Полный поиск ответов сохранён.
- `doctor --verify-history`, `--rebuild-index` и `--export` доступны онлайн и при остановленном сервисе. Индексы производны; сбой их сохранения не отменяет подтверждённую операцию. Диагностический экспорт исключает личное содержимое.
- Стабильные коды ошибок задают объяснение и следующее действие CLI. MCP сохраняет три публичных инструмента.

## Сохранённые исправления 0.2.1

- Запуск, продолжение и отмена задачи согласованы между собой. При закрытии сервис завершает принятые запросы и ждёт остановки исполнителей; ошибка одного модуля не прерывает закрытие остальных.
- Неполная запись пакета событий откатывается. Если откат журнала не удался, дальнейшие изменения блокируются до перезапуска, а CLI показывает причину остановки.
- Неизвестный результат записи требует проверки человеком. Проверка недоступна, пока исполнитель ещё работает; подтверждённые действия не повторяются автоматически.
- Прерванное восстановление файла можно проверить командой `resolve-restore` или через карточку задачи. Сравнение с сохранёнными версиями фиксирует фактический результат без автоматической перезаписи текущего файла.
- Продолжение беседы учитывает цепочку задач даже при переводе системных часов назад. Неизвестные результаты проверяются во всей сессии, включая скрытые этапы; поздние исправления человека поступают незавершённым агентам без нарушения порядка вызовов и ответов инструментов.
- Добавлены регрессионные сценарии для ошибок диска, закрытия IPC, одновременной отмены и запуска, восстановления файлов и продолжения после сбоя.

## Изменения в 0.2.0

- Сообщение работающей задаче через **Ctrl+W** в карточке или команду `message`: отдельный черновик, сохранённая очередь и защита от повторной отправки с тем же ключом. Координатор получает сообщение после завершения текущего обмена с инструментами.
- Восстановление делегирования после сбоя сохраняет завершённую работу и не запускает потомков уже завершённой или неудачной ветки.
- Функции и методы исходного кода дополнены кратким JSDoc на русском языке; документация актуализирована, устаревшие отчёты удалены.
- `.gitattributes` сохраняет окончания строк LF при checkout на Windows; проверки видимого текста CLI учитывают ANSI-оформление цветного терминала.

Версия согласована в `package.json`, корневых записях lockfile, CLI, `system.info`, MCP-клиенте, MCP-сервере и подключении Codex. После обновления файлов перезапустите сервис Harness, чтобы он использовал новую сборку.

## Исправленные дефекты

- Запуск CLI через символическую ссылку раньше завершался без вывода: путь `argv` не совпадал с путём модуля. Проверка главного модуля заменена на `import.meta.main`. Импорт `createCli` по-прежнему не запускает обработку команд.
- Отмена зависшего npm могла оставить подготовку занятой. Компилятор, установка библиотек и проверка Node/npm используют `scripts/preparation-command.mjs`: ошибка отмены или таймаута сохраняется даже при выходе обработчика сигнала с кодом 0. Через секунду после SIGTERM процесс принудительно завершается; harness ждёт `close`.
- Сохраняемый в памяти вывод проверок runtime ограничен 64 КиБ. Проверка дерева npm ограничена минутой, установка — 15 минутами. Прерывание установки не заменяет прежнюю сборку и не записывает успешный маркер подготовки. Пользователь может повторить запуск.
- Проверка SHA256 на Windows использует `Get-FileHash -LiteralPath`, чтобы квадратные скобки в названии папки не интерпретировались как шаблон. Это исправление проверено по контракту PowerShell; нативного запуска Windows в этом окружении не было.
- Пробный `npm pack` захватывал фиктивный `.env.production` и исключал необходимые bootstrap файлы. Состав npm-пакета ограничен, а поддерживаемая поставка создаётся отдельной командой `release:pack`.

Подготовка управляет принадлежащими ей процессами: группой процессов на POSIX и деревом через `taskkill` на Windows. Это не изоляция ОС; сторонние программы и процессы, самостоятельно вышедшие из группы, находятся вне этого механизма.

## Поставка исходников

```sh
npm run check
npm run release:check -- --full
```

Первая команда проверяет рабочую копию. Вторая создаёт `releases/harness-0.3.1-source.zip`, проверяет SHA256 и внутренний манифест, распаковывает выпуск во временную папку с пробелами, кириллицей и квадратными скобками, затем устанавливает библиотеки и выполняет проверки. Node берётся из уже запущенного закреплённого runtime; этот сценарий не проверяет доступность сервера загрузки Node. Облачные модели не вызываются, пользовательские задачи и настройки не используются.

ZIP создаёт библиотека [fflate](https://github.com/101arrowz/fflate), закреплённая в devDependencies и lockfile. Внутри находятся исходники, тесты, необходимые скрипты, конфиги, примеры, Markdown-документация, lockfile и файлы запуска. Даты и Unix-права в ZIP фиксированы; одинаковые входные байты дают одинаковый архив. Для `start.sh` и macOS `.command` сохраняется право исполнения.

Список допустимых файлов находится в `scripts/release-pack.mjs`. Символические ссылки и специальные файлы в разрешённых путях отклоняются. `.git`, `.env*`, скрытые вложенные файлы, `.harness`, `.tools`, `dist`, `node_modules`, предыдущие архивы и локальные логи в ZIP не входят. Это проверка состава поставки: она не распознаёт секреты, вручную вписанные автором в разрешённый исходник или конфиг.

`release-manifest.json` содержит версию, SHA256 и режим каждого файла; соседний `.zip.sha256` проверяет целостность архива. Они не являются цифровой подписью автора. ZIP и файл суммы публикуются отдельными переименованиями: прерывание между ними обнаруживается проверкой суммы, после чего следует повторить упаковку.

## Проверки и доказательства

Регрессионные тесты проверяют прямой запуск и ссылку из чужой рабочей папки, импорт без побочных действий, сохранение аргументов, отмену игнорирующего SIGTERM npm, отсутствие оставшихся проверочных процессов, откат каталога runtime, предел вывода и ошибки запуска. Тесты упаковки проверяют исключение фиктивных приватных файлов, обязательные конфиги, режимы ZIP, воспроизводимость и согласованность package/lock.

`releases/release-check.json` появляется только после успешной проверки текущего архива; старый успешный отчёт удаляется перед новым прогоном. Подробности сохраняются в `releases/release-check.log` и `releases/release-install.log`. Эти файлы создаются заново при проверке и не включаются в ZIP.

Workflow CI предусматривает проверки на Ubuntu, macOS и Windows и отдельно проверяет распакованный ZIP. Наличие workflow не означает успешный запуск GitHub Actions. Локальная проверка текущего выпуска и результат CI учитываются отдельно; нативный Windows-прогон нельзя подтверждать результатами macOS или Linux.

## Измерение большой истории

```sh
npm run benchmark:storage -- 1000 releases/storage-1000.json
npm run benchmark:storage -- 10000 releases/storage-10000.json
```

Стенд создаёт временные задачи без обращения к модели. Отчёт показывает первичное построение каталога, открытие готовых индексов в отдельном процессе, RSS, размер источников и производных данных, p95 списка со счётчиками, первый и повторный поиск полного ответа. На Linux CI p95 выше 200 мс завершает проверку с ошибкой. Прогон не читает пользовательское состояние. Время первого построения индексов следует отличать от обычного запуска уже проиндексированного архива.
