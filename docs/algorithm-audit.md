## Что стало проще

Восстановление незавершённых вызовов сосредоточено в `recoverInterrupted`. Его вызывают только после остановки исполнителей: при старте сервиса или после завершения дерева. Проверка статуса корня больше не заменяет проверку фактических вызовов.

Общий предикат `requiresOutcomeReview` используется при продолжении, новом вопросе в той же беседе и очистке данных. Отмена задачи не даёт обойти проверку начатой записи новым пользовательским ходом. Поздний ответ с ограничением провайдера также не возвращает отозванное задание обучения в очередь.

У сохранения теперь одна точка подтверждения — завершённая синхронизированная запись JSONL. `writeSnapshot` применим только после неё. Отказ производной JSON-копии не меняет уже записанный результат. Обязательные записи состояния, которые не имеют такого журнала, продолжают использовать обычную атомарную запись с возвратом ошибки.

Исполнитель различает ошибку самой операции и ошибку обработки уже полученного результата. Общий `markUnknown` закрывает пути остановки после возможного побочного эффекта. Ошибка чтения остаётся обычным результатом ошибки: ручная проверка внешнего изменения ему не нужна.

Регистрация файловых инструментов содержит их схемы и подключение. Пагинация списка и ограниченный поиск находятся в отдельных небольших файлах; признаки неполноты поиска не смешиваются с признаком сохранённого артефакта.

Отзыв подтверждений, уроков и зависимых выпусков вынесен из очереди обучения в отдельный модуль. Правила отрицательной обратной связи описаны в [документе об отзыве знаний](learning-feedback.md). Версии уже начатых задач остаются зафиксированными.

## Проверки

Для дефектов сохранения результата, снимка, восстановления paused-записи, отзыва знаний и пустого потока сначала воспроизведено прежнее поведение. Регрессии используют временные каталоги, настоящие журналы и управляемые сбои `EIO`, `EISDIR`, `ENOSPC` и ограничения провайдера.

Отдельно проверены инварианты очереди при 1, 2 и 4 чтениях: запись не пересекается с чтением, следующие операции не обходят предшествующую запись, ошибка освобождает блокировку, отмена ожидающей записи снимает её барьер. Параллельные операции проверяются по порядку наблюдаемых событий.

Файловые проверки создают каталоги с 501 и 1001 записью, проверяют точные границы выдачи, ошибки доступа и отмену. Реальные пользовательские задачи, файлы проектов и состояние сервиса в этих сценариях не изменяются.

Если весь ответ инструмента превышает размер выдачи, общий механизм сохраняет его в артефакт. В этом случае карточка сообщает о большом результате; подробные `incomplete` и `reason` поиска доступны в полном артефакте. Короткие неполные результаты показывают предупреждение непосредственно в журнале.

## Следующая граница масштабирования

Текущий JSONL хранит полный снимок запуска в каждой записи, а хранилище держит исторические снимки в памяти. По мере роста переписки растут и размер события, и число событий: для длинной задачи стоимость может расти квадратично. Это видно из `FileSessionStore.persist`, без предположений о провайдере.

Следующее отдельное изменение — события с изменениями состояния, периодические снимки и чтение истории страницами с диска. Для него нужны новая версия формата, миграционные тесты и воспроизведение всех точек аварийного восстановления. В текущих исправлениях формат сохранён: перенос хранения не смешан с устранением ошибок исполнения.

Поддержка удобнее, когда каждая такая граница имеет один владеющий модуль и тест на прерывание до и после записи. Новая общая шина событий, дополнительные сервисы и новые зависимости для этих исправлений не потребовались.
