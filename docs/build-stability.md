## Устройство подготовки

- `scripts/build-state.mjs` вычисляет отпечатки исходников, конфигов, runtime и выходных файлов; записывает JSON-маркеры через временный файл и переименование.
- `scripts/build.mjs` компилирует, проверяет CLI и публикует сборку. Проверка справки ограничена 10 секундами, компиляция — 5 минутами. Проверка использует отдельный каталог состояния. Изменение исходников во время сборки отменяет публикацию.
- `scripts/project-lock.mjs` исключает одновременную подготовку одной папки при сборке, установке библиотек и восстановлении Node. Используются встроенные модули Node: установка дополнительной библиотеки до `npm ci` не нужна.
- `scripts/bootstrap.mjs` проверяет кэш, при необходимости выполняет `npm ci`, вызывает общий сборщик и сохраняет журнал в `.tools/setup.log`. Повторная подготовка исправного кэша не перекомпилирует приложение.
- `scripts/install-runtime.mjs` обслуживает POSIX- и Windows-файлы запуска. Загрузка и проверка SHA256 архива остаются в соответствующем launcher-скрипте.

Перед заменой `dist` прежний каталог переименовывается в `.harness-dist-backup`. Если публикация завершается ошибкой, он возвращается на место. После аварии между переименованиями следующий запуск восстанавливает резервный каталог до компиляции либо удаляет его, если новая сборка уже цела. Это две операции переименования, а не неделимая транзакция файловой системы; уже запущенный процесс с ленивыми импортами не получает гарантии непрерывного доступа к старому `dist`.

Временные каталоги `.harness-build-*` и `.harness-dist-backup` исключены из Git, Docker-контекста и форматирования. После обычного завершения и обработанной отмены временная сборка удаляется; после `SIGKILL` может остаться неактивный временный каталог.

Mutex занимает один порт только на `127.0.0.1`, выбранный по каноническому пути проекта. Коллизия с другой папкой или посторонним процессом даст отказ «канал подготовки занят»; параллельная запись при этом не разрешается. SIGINT/SIGTERM передаются выполняющейся подготовке. Принудительное завершение родителя через SIGKILL не гарантирует завершения всего дерева уже запущенных им программ.

## Регрессионные проверки

`test/build-pipeline.test.ts`, `test/bootstrap.test.ts` и `test/launcher.test.ts` используют временные проекты и настоящие процессы Node/npm/TypeScript. Они проверяют воспроизводимость повторной сборки, удаление старых модулей, source maps, сохранение рабочей сборки при ошибках и таймауте, отмену, сбой публикации, восстановление резервного каталога, конкурирующие процессы, старый пустой lock, пути с пробелами, повреждённые пакеты, некорректные JSON-маркеры и перенос runtime. Загрузка Node в launcher-тестах заменена локальным архивом: эти тесты не подтверждают доступность внешнего сервера загрузки.

## Проверки CI

`.github/workflows/check.yml` сохраняет матрицу Ubuntu, macOS и Windows. Каждый запуск записывает точные версии Node/npm и архитектуру, выполняет `npm ci --include=dev --include=optional` из lockfile и общий `npm run check`. После этого файл запуска дважды проходит `--prepare-only`, затем открывает справку через `--help`. В Windows проверяется тот же PowerShell-скрипт, который вызывает пользовательский `.cmd`.

Отдельная задача собирает `Dockerfile.test` с прежним закреплённым digest Node 24.21.0 и выполняет проверки от пользователя `node` без внешней сети. Ubuntu дополнительно запускает `scripts/playtest-source-bugs.py` в настоящем PTY с `pyte==0.8.2`: временный сервис, длинный вывод команды и постраничное чтение большого ответа. Облачные модели и пользовательские данные этому сценарию не нужны.

Логи проверок, свежий JSON-отчёт PTY и его кадры сохраняются на семь дней даже при ошибке. В архив входят только явно подготовленные файлы из временного каталога CI; каталоги состояния, конфиги, ключи и весь `.harness` не загружаются. Прежний отчёт удаляется перед PTY, чтобы сбой запуска не выдавал исторический результат за новый.

Actions закреплены SHA коммитов официальных репозиториев: checkout/setup-node v4, setup-python v5, upload-artifact v4. Эти SHA проверены через соответствующие теги 13 сентября 2026. Зависимости проекта и базовый Docker-образ не обновлены.

## Границы проверки

Наличие workflow не означает успешный запуск GitHub CI: результат появляется только после публикации репозитория и выполнения задания. `*-latest` оставлены для совместимости существующей матрицы; версии runner-образов и все сочетания ОС/архитектуры пока не закреплены. Отчёт окружения показывает фактическую машину каждого запуска. Нативный Windows и его терминальный интерфейс нельзя считать проверенными по локальному прогону macOS/Linux; PTY-сценарий пока выполняется только на Ubuntu.
