# Работа специалистов и измерения исполнения

В 0.7.0 карточка задачи показывает дерево специалистов, текущие фазы, результаты и расход. В проекте запуски разделены по этапам и попыткам; переход к проверкам сохраняет связь с конкретным исполнением. Просмотр использует сохранённые данные и не вызывает дополнительную модель.

## Как открыть

В действиях задачи выберите «Работа специалистов». В карточке проекта доступен одноимённый раздел с отдельными запусками. Экран обновляется во время работы; выбор специалиста, вкладка и положение чтения сохраняются.

```sh
harness insights RUN_ID
harness --json insights RUN_ID
harness projects insights PROJECT_ID
harness --json projects insights PROJECT_ID --offset 20
```

У специалиста есть вкладки задания, времени и токенов, журнала и результата. Журнал выдаётся страницами до 100 событий, результат — по 16 384 символа; переход к следующей странице доступен через действия. Большое задание или ошибка показываются с явной отметкой фрагмента.

Список специалистов открывается страницами по 50 записей в порядке создания. API допускает до 100 записей за запрос и возвращает общее количество; отдельная карточка получает только выбранного агента. Сводка показывает до 256 последних эпизодов ролей с отметкой о сокращении, полный технический журнал остаётся доступен постранично.

Модель может сообщить о завершении своей работы; прохождение проверки подтверждается отдельным результатом проверки. Карточка не превращает ответ «готово» в доказательство.

## Что означает время

| Поле или фаза                       | Что измеряется                                                                                                           |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Работа задачи (`activeMs`)          | Время запущенного дерева, включая ожидания внутри него; параллельные ветки не прибавляются к нему повторно               |
| Пауза (`pauseMs`)                   | Пауза между исполнениями, пока жив тот же локальный сервис                                                               |
| Работа специалиста (`agent`)        | Интервал агента, включая вложенные операции и ожидания                                                                   |
| Очередь модели (`model.queue`)      | Ожидание места в ограничителях Router и SDK; два интервала последовательны                                               |
| Запрос к модели (`model.request`)   | Одна попытка адаптера, включая его подготовку и завершение транспорта                                                    |
| Первый ответ (`model.first_output`) | Время от начала попытки до первого непустого текста, опубликованного пояснения или структурированного вызова инструмента |
| Повтор (`model.retry`)              | Ожидание перед следующей разрешённой попыткой; не входит во время предыдущего запроса                                    |
| Очередь и инструмент                | Ожидание диспетчера и само исполнение разделены                                                                          |
| Разрешение и специалисты            | Ожидание решения человека и дочерних веток разделено                                                                     |
| Планирование и сжатие               | Внешние фазы, внутри которых также могут находиться запросы модели                                                       |

Фазы вложены и могут пересекаться. Их сумма не равна времени пользователя. Первый фрагмент является частью запроса, а запрос — частью работы агента. Это измерения Harness, а не загрузка процессора модели или чистая задержка её сервера. Для Codex в попытку входит подготовка и закрытие эфемерного app-server.

Длительности вычисляются по монотонным часам процесса; календарное время служит меткой события. Смена системных часов не изменяет уже измеренную длительность. После перезапуска незакрытая фаза обозначается как прерванная; время выключенного сервиса к работе модели или паузе не прибавляется.

Handoff сохраняет `agentId`, но начинает отдельный эпизод роли и профиля. После завершения исполнения временные связи эпизодов освобождаются; сохранённый журнал продолжает хранить предыдущие участки.

## Токены и полнота

Расход одной попытки относится к одной категории:

- `provider` — значения прислал провайдер. Нулевое значение допустимо, если оно действительно получено.
- `estimate` — адаптер использовал совместимую оценку из размера данных. Это не точный tokenizer модели и не счёт к оплате.
- `unavailable` — расход неизвестен; в событии стоят `null`, в сводке растёт число попыток без данных.

Повторы имеют собственные номера и расход. Неуспешная попытка сохраняет известный usage, если он был получен до ошибки. Накопительные уведомления Codex и статистика отдельных ответов не складываются между собой повторно. Прежнее числовое поле `ModelOutput.usage` сохранено; дополнительное `usageSource` объясняет его происхождение.

Подробные метрики имеют полноту `complete`, `partial` или `unavailable`. `complete` означает доступность записанных измерений, но не обещает наличие usage у каждого провайдера. `partial` обозначает пропущенные события, прерванные интервалы или неизвестные части измерений. Для старой задачи без отдельного журнала используется `unavailable`; её прежний общий расход показывается отдельно без выдуманного распределения по специалистам.

## Хранение и API

Все пути ниже находятся внутри управляемого состояния Harness:

| Данные                           | Путь                            |
| -------------------------------- | ------------------------------- |
| Технические события              | `activity/<runId>.jsonl`        |
| Устойчивый признак потери данных | `activity/<runId>.json`         |
| Производный индекс и сводка      | `indexes/activity/<runId>.json` |

События версии 1 связывают запуск, агента, эпизод роли, профиль, запрос или вызов инструмента, попытку, фазу и исход. Они не содержат переписку, аргументы инструментов и ключи. Тексты задания и результата на экране читаются из обычной задачи и не копируются в журнал метрик.

Очередь записи ограничена учётным размером 1 МиБ; исторический кэш сводок — 16 МиБ. Это лимиты конкретных структур, а не всей памяти процесса. При сворачивании сохраняется до 4 096 эпизодов и открытых интервалов; достижение предела отмечает данные как неполные. Журнал читается потоково, разреженные смещения создаются через 128 событий. Меню обычных задач не перечитывает все переписки ради метрик.

Ошибка записи метрик или переполнение не меняют итог пользовательской операции. При возможности сохраняется отметка о неполноте; полный отказ диска может помешать сохранить и её. Повреждённый технический журнал не дописывается, читатель не чинит его на месте. Отсутствующий или устаревший индекс пересоздаётся из источника. Полное удаление задачи и выбранный сброс охватывают метрики, индексы и кэш.

Локальные команды `runtime.insights`, `runtime.activity`, `projects.insights` доступны при возможности `execution-insights-v1` в `system.info`. Клиент старого сервиса скрывает новые действия. Версия протокола остаётся 1; публичные MCP-инструменты не расширены.

## Сравнение режимов

Без подключений и API-ключей:

```sh
harness benchmark specialists --output ./specialists-offline
```

Каталог должен быть новым. Стенд создаёт в нём 45 изолированных запусков: пять сценариев × три режима × три повтора. Подготовленный провайдер проходит настоящий runtime, инструменты и доверенные проверки. Этот результат проверяет механизм стенда и не доказывает полезность делегирования для реальной модели.

Режимы: `solo` — один агент; `fixed` — заданный начальный план; `auto` — существующий автоматический выбор команды. Сценарии: независимые файлы, связанный рефакторинг, исправление теста, исследование и пересекающиеся изменения. Проверки расположены вне изменяемой папки; исполнитель разрешает только закреплённую команду проверки.

Для ручного сравнения реальной модели:

```sh
harness benchmark specialists --real --config ./config/harness.json --profile qwen --output ./specialists-qwen
```

Выберите имя профиля из своей конфигурации. CLI сначала покажет сценарии, модель, роли и пределы, затем запросит подтверждение. При неинтерактивном запуске требуется явный флаг `--confirm-real`. Это 45 отдельных задач, а не 45 API-запросов: фактическое число запросов и возможный расход зависят от ответов модели. Наличие инструкции не запускает такое сравнение автоматически.

Стенд использует собственные роли `coordinator`, `executor`, `researcher`, `reviewer`, отдельные папки и состояние. Из пользовательской конфигурации берётся выбранный профиль; обычные задачи и настройки не изменяются. Обучение выключено, закреплена исходная версия опыта. Пределы стенда: четыре агента, глубина два, два запроса модели одновременно, 64 шага и 180 секунд на отдельный запуск.

`report.json` и `report.md` сохраняются после каждой попытки. В них есть результаты фиксированных проверок, профиль и хеш параметров, хеши сценариев и конфигураций, время и категории токенов. `wallMs` включает подготовку, исполнение, проверку и закрытие изолированного приложения; `activeMs` отдельно отражает работу runtime. Результаты и артефакты находятся в `runs/` рядом с отчётом.

Ctrl+C останавливает принадлежащие стенду исполнители и сохраняет частичный отчёт. Повтор команды создаёт новый каталог и начинает новое сравнение; автоматического продолжения старого стенда нет. Отчёты и учебные папки остаются для анализа, пока пользователь сам их не удалит.

В проверку поставки входит офлайн-прогон. Реальные платные модели не вызываются как скрытая часть релиза или CI. Для вывода об эффективности нужны явно принятый реальный прогон, анализ неудач и независимые контрольные случаи. [Следующий шаг по результатам измерений](specialists-plan.md).

## Границы для разработчика

`ExecutionObserver` создаёт наблюдателя с контекстом запуска; `ExecutionObservation` принимает только начало/конец фазы и итог usage. Runtime, контекст и инструменты зависят от этого порта, а `application` подключает файловый адаптер `insights`. Модуль `benchmark` собирает самостоятельные приложения для каждого случая.

Встроенные провайдеры объявляют `observesRequests = true`: они измеряют собственные очереди и повторы. Для внешнего адаптера без этого признака runtime измеряет один вызов `generate` и доступные фрагменты на своей границе. Его внутренние повторы неизвестны; старый расход без `usageSource` не становится подтверждённым. Обёртка инструментированного адаптера должна объявить этот признак и передать `request.observation` внутрь, чтобы сохранить детализацию без двойного учёта.

Этот выпуск добавляет наблюдение. Он не меняет правила делегирования, последовательность мутаций, разрешения, лимиты пользовательских задач или алгоритмы обучения. Вывод о следующем изменении принимается по результатам измерений.
