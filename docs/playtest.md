## Путь неподготовленного пользователя

В настоящем терминале пройдён весь сценарий: выбор папки с пробелами и кириллицей, выбор совместимого сервера, ошибочный ключ → исправление, получение списка моделей, запуск сервиса в том же окне, запись с однократным разрешением, сохранение ответа, уточнение в той же сессии и возврат в меню по Esc. После закрытия и повторного запуска восстановлены настройки и история. В окне шириной 48 колонок проверены просмотр результата, Ctrl+C, выход с работающей задачей и освобождение блокировки. Значения тестовых ключей отсутствуют в выводе и файлах состояния.

13 дополнительных тестов проверяют мастер, каталог трёх провайдеров, временные ключи, отдельное владение сервисом, разрешения, продолжение сессии, сохранение без перезаписи и ошибки диагностики. Ещё один тест фиксирует гонку отмены.

Найдено и исправлено:

- Clack spinner завершал процесс при Esc. Подготовка использует Ora; просмотр задачи теперь рисует log-update с управлением клавишами на стороне приложения.
- После одобрения короткий промежуток без pending-разрешений считался окончанием задачи. Ожидание продолжается до актуального состояния.
- Ошибка API при abort могла записаться поверх отмены. Намерение отмены фиксируется до abort, отдельный тест проверяет журнал.
- Диагностика могла выбрать конфиг из текущей папки вместо конфига подключённого сервиса. Теперь проверяется конфиг сервиса; ошибка диагностики в меню не меняет код последующего штатного выхода.

Структурированный отчёт: [playtest-cli.json](playtest-cli.json). Воспроизведение на macOS/Linux: `python3 scripts/playtest-cli.py --node /полный/путь/к/node-24.21.0`. Скрипту нужен Python 3 со стандартной библиотекой; сторонние Python-пакеты не требуются.

Файл `start.sh` отдельно проверен с нуля в новой папке с кириллицей: скачивание официального runtime, проверка SHA-256, установка и сборка. Повторный запуск использовал кеш. Отчёт: [playtest-launcher.json](playtest-launcher.json). Windows-файлы запуска подготовлены, но нативно не проверены.

## Сквозной OpenCode

OpenCode подключился к MCP и сам вызвал `harness.run` и `harness.status`. Harness получил ошибочные аргументы записи, вернул ошибку, принял исправленный вызов, записал и прочитал файл. Затем обучение извлекло урок из результата чтения, выполнило три сравнения каждой версии на целевом и контрольном случаях и опубликовало выпуск. Исходный запуск остался на `baseline`, следующий получил новый выпуск и применил урок. Ручной откат вернул активную версию на `baseline`.

В финальном прогоне локальный HTTP-сервер обработал 14 запросов со стороны OpenCode, 8 запросов пользовательских запусков harness, 1 извлечение урока и 12 оценочных запросов. Запросы OpenCode включают его служебную работу; это не число вызовов MCP.

**Ответы моделей задавались управляемым локальным HTTP/SSE API.** Реальными были OpenCode, MCP, сервис, CLI, библиотеки провайдеров, файловые эффекты, политики, хранилища и публикация. Сценарий проверяет исполнение протоколов и механизм обучения, но не качество рассуждений облачной модели.

## Аварийный сценарий

1. Модель запросила локальную команду, политика выставила `ask`.
2. Через локальный управляющий интерфейс было выдано однократное разрешение.
3. Команда записала `x` в счётчик и осталась работать.
4. Сервис завершён сигналом SIGKILL после побочного эффекта. Созданная тестом группа процесса ОС явно остановлена.
5. Новый сервис восстановил запуск как `paused`, а мутацию — как `unknown`.
6. Попытка `resume` до проверки результата отклонена.
7. Человековладелец через локальный управляющий интерфейс зафиксировал фактический результат; CLI выполнил `resume`.
8. Счётчик по-прежнему содержал ровно `x`: повторной команды не было.

Автоматический сценарий подаёт человеческое решение непосредственно через локальный IPC. Дополнительно в настоящем PTY пройдены выбор операции, просмотр точных аргументов, одобрение стрелкой и Enter, затем отказ с выбранным по умолчанию «Нет». На локальном тестовом API выполнены две настоящие задачи: одобренная команда создала `approved.txt` с ожидаемым содержимым; отклонённая команда не создала `denied.txt`. Оба запуска завершились, список ожидающих решений пуст. MCP операции одобрения не предоставляет.

## Проверка терминального интерфейса

В настоящем PTY проверены логотип и экран готовности сервиса при 80 колонках, компактный логотип и меню при 40 колонках, переход стрелкой и Enter к пустому списку запусков, диагностика, карточка разрешения с длинным путём, одобрение и отказ. После исправления карточка помещается в узкий терминал и сохраняет полный текст аргументов.

Отмена ввода задачи через Ctrl+C завершилась кодом 130. Сервис штатно остановился по Ctrl+C; сокет и блокировка удалены. При перенаправленном stdin и терминальном stdout справка содержит один логотип. Настоящий MCP-клиент подтвердил, что оформление не нарушает stdio-протокол.

## Исправления по результатам проверки

- UTF-8 больше не повреждается при разделении символа границей пакетов Unix-сокета.
- Условно разрешённый инструмент отображается модели, а конкретные аргументы проверяются при вызове.
- Отмена задания снимает его с очереди, не ожидая чужую операцию или запрос модели.
- Ошибка дочерней роли останавливает её потомков до итогового ответа корня.
- Потерянный ответ внешней мутации переводит запуск в `unknown/paused`.
- Отменённое разрешение не остаётся в списке ожидающих решений после остановки пакета.
- Роль доказательства фиксируется на момент вызова и не меняется задним числом после handoff.
- История после перезапуска сортируется по времени, а не по случайному UUID имени файла.
- Новый сервис не продолжает старый запуск с изменённой классификацией MCP или сервисными лимитами.
- Журнал обучения восстанавливает опубликованную версию даже при устаревшем снимке и оборванном последнем событии.

Повторная проверка после рефакторинга также исправила восстановление обучения при повреждённом JSON-снимке, освобождение блокировки при неудачной подготовке сокета, перенос длинных аргументов в карточках и неинтерактивный режим `--json approvals`. Подробности: [maintainability.md](maintainability.md).

## Границы проверки

Облачный Qwen **не проверен**: профиль с доступным API-ключом не был предоставлен; `doctor` подтвердил отсутствие настроенных ключей в окружении тестового сервиса. Прямые API OpenAI, Anthropic и Google также не вызывались. Через аккаунт Codex выполнен настоящий маршрут MCP → Harness → Codex → fs.read: случайное значение прочитано и проверено, в текущем повторе — три модельных обращения. Модель дважды прочитала тестовый файл; обе операции только читали, итоговое значение совпало. Доступность конкретных моделей в аккаунтах и качество автоматически предлагаемых ими уроков требуют отдельного прогона с ключами и предметным контрольным набором.

Тесты не доказывают универсальную защиту от смысловых prompt injection. Машинные полномочия принудительно отделены от текста уроков и результатов; публикация ограничена проверенным контрольным набором. Произвольная локальная команда работает с правами пользователя ОС.

Нативный Windows, иные версии Node, распределённое исполнение и нагрузочная устойчивость больших журналов не проверялись. Linux arm64 проверен в контейнере; подробности и сценарии первого запуска — в [portability.md](portability.md). Развёртывание, публикация пакета и push в Git не выполнялись.

## Дополнительный проход удобства

- Проверены ограничители задачи и дня до отправки API, совместное резервирование, учёт возможных повторов, сохранение квоты после ошибки и перезапуска, явное увеличение и продолжение.
- Проверены diff, резервная копия, восстановление после перезапуска, удаление созданного файла при откате, сохранение ручных правок и отказ при подмене пути ссылкой.
- Проверены поиск старых задач и ответов, закрепление активных задач, сохранение подпапки, недавние проекты, смена модели без изменения авторских правил.
- Ключи разделены по подключению; отмена настройки возвращает ключ действующего подключения. В macOS фактически проверены запись, чтение и удаление временного секрета: `playtest-keyring.json`.
- Терминальный сценарий дополнен поиском, восстановлением файла, выбором хранения ключа и экраном квоты. Логи не содержат введённые тестовые ключи.
- Smoke прямого облачного API подготовлен, но в нём API не вызывался: отсутствовал ключ в окружении проверки. Отчёт `playtest-cloud.json` явно отмечает это состояние.

Используются NestJS 11.2.3, Vitest 4.1.11 и Vite 7.3.6. В исходном дереве зависимостей были критические и высокие предупреждения npm audit; обновление их устранило. Оставшиеся пять low относятся к одной транзитивной проблеме старой ветки AI SDK. До парсера SDK теперь установлен лимит сырых данных 8 МиБ, включая SSE без разделителей; отказ и закрытие потока покрыты тестом. Это ограничение не означает отсутствие предупреждений npm audit. Подробности — `dependency-audit.md`.

Полный `npm run check` прошёл: 124 теста в 18 файлах на macOS arm64 и Linux arm64, Node 24.21.0. Linux использовал отдельные зависимости контейнера и актуальную папку `test`, подключённую только для чтения. ## Понятное меню, продолжение и полное удаление

Итоговый `npm run check` прошёл на **macOS arm64 и Linux arm64: 235 тестов в 31 файле**. Проверены требования зависимостей, форматирование, типы, сборка и все unit/integration-сценарии. - Длинные подсказки меню занимают доступную ширину и переносятся целиком. Убраны преждевременные многоточия, пассивные сообщения об обновлении и счётчик страницы, когда весь список помещается. Вместо `baseline` показано «Без накопленного опыта».

- «Убрать из списка» сохраняет историю. «Удалить навсегда» сначала показывает состав всей переписки: этапы, внутренние артефакты, резервные копии и связанные знания. - При неизвестном результате прерванной операции продолжение и удаление недоступны до её проверки человеком. Подтверждённые факты учитываются после завершённых обменов вызов–результат и перед новым вопросом. Уже выполненные изменения автоматически не повторяются.

Содержимое удалённой переписки исчезает из внутренних журналов; для запрета повторного исполнения остаются только идентификаторы, хеш ключа запроса и числовой учёт квоты.

Настройки меню имеют приоритет для новых задач и сохраняются в `iteration-settings.json`; отдельной задаче на паузе можно задать свой предел. Достижение предела сохраняет всё дерево на паузе. Продолжение выдаёт следующую порцию шагов, не сбрасывая общую историю и не повторяя завершённые инструменты.
- Проверены совместимость старых сохранений после исчерпания квоты, перезапуск сервиса, общие шаги дочерних агентов, неизменность снимка конфигурации и версии опыта. Неизвестный результат операции требует проверки человеком. Устаревшее подтверждение настроек, работающая и удалённая задача не позволяют перезаписать предел.
- Ошибка текущего авторского конфига не мешает читать состояние уже сохранённой задачи. Настройки новых задач подхватывают изменения базового конфига без перезапуска, если пользователь ещё не сохранил приоритетное значение через меню.

Настоящий PTY при **48×24 и 80×24** прошёл **24 проверки предела шагов в 62 кадрах** и **16 проверок снятия квот в 22 кадрах** на той же финальной JavaScript-сборке. В обоих сценариях после настоящей записи файла сервис перезапускался; продолжение завершалось без второго вызова записи и без изменения времени модификации файла. Для шага обучения терминальный сценарий проверяет живое отображение учёта, а снятие лимита очереди и её восстановление подтверждены интеграционными тестами.

Все модельные сценарии этого прохода использовали временные данные и локальные тестовые провайдеры. Облачный Codex/Qwen и нативные терминалы Windows/Linux повторно не проверялись. Прежний общий проход 46 живых экранных проверок относится к промежуточной сборке до настройки шагов; его SHA сохранён в карте экранов. Структурированные результаты: [платформы и состояние](playtest-quota-resume-platforms.json), [предел шагов](playtest-iterations.json), [снятие квот](playtest-no-quota.json).

На финальной сборке также повторно прошли **30 проверок полировки и выхода** и **18 основных проверок CLI**. Подготовка через `start.sh --prepare-only` завершилась успешно, повторная подготовка использовала кеш; SHA JavaScript сохранился. Обновлённый CLI открыт в Terminal. Локальный API подтвердил отсутствие токеновых квот и активных запусков. Новым задачам через API установлен предел 256; сохранённая пользовательская задача осталась на паузе после 12 шагов со своим прежним пределом 64. Её снимок побайтно не изменился, автоматическое продолжение не запускалось. Предел этой задачи можно отдельно изменить на паузе.
