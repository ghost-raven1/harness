# Подключение к Codex

Доступны оба направления: Codex вызывает Harness через MCP, а Harness использует модели аккаунта Codex для выполнения задач.

## Codex внутри Harness

Откройте «Запустить Harness» → «Codex · мой аккаунт · без ключа API». Если вы уже вошли в Codex на этом компьютере, мастер предложит доступные модели. Иначе он запустит официальный вход через браузер. Для смены модели: «Настройки → Подключить другую модель → Codex».

Вход обслуживает официальный пакет `@openai/codex@0.154.0`. Harness не копирует токены авторизации в свою конфигурацию и не требует отдельного API-ключа. Приложение не обновляет глобальную установку Codex. Рабочий каталог и выбранная модель сохраняются для следующего открытия CLI.

Настройки профиля:

```json
{
  "codex": {
    "provider": "codex",
    "baseUrl": "codex://account",
    "model": "ID из каталога вашего аккаунта",
    "retries": 0,
    "outputTokens": 8192,
    "timeoutMs": 120000
  }
}
```

`baseUrl` обозначает способ авторизации; это не адрес HTTP-сервера. Единственная дополнительная опция — `options.effort`, со значением, поддерживаемым выбранной моделью.

### Исполнение и ограничения

Адаптер использует официальный app-server. Для каждого обращения создаётся временный поток без доступа к среде и рабочей папке Codex. Собственные shell, MCP, skills, hooks и дочерние агенты Codex отключены. Авторские инструкции Harness передаются отдельно от JSON-истории. Пользовательские инструкции самой установки Codex могут присутствовать в дополнительном контексте; машинные политики Harness действуют независимо от текста модели.

Модель получает динамические инструменты Harness. Адаптер ждёт подтверждения полного ответа, возвращает структурированные вызовы и завершает процесс Codex. Затем обычный диспетчер Harness проверяет схему, права и разрешения. История, handoff, compaction, изменения файлов и обучение остаются в Harness. Результат похожей на JSON строки в обычном тексте не исполняется.

App-server не предоставляет контракт `max_output_tokens` для каждого запроса. Поэтому лимит Harness для Codex является оценкой, а не гарантией максимального списания токенов: расход проверяется после ответа, тайм-аут и отмена завершают процесс. Точные лимиты подписки показывает Codex. Если выход превысил бюджет, ответ не считается успешно завершённым. Версия app-server зафиксирована; обновление требует повторной проверки протокола и списка доступных инструментов.

## Harness как MCP-сервер в Codex

1. Оставьте окно Harness открытым: оно владеет локальным сервисом.
2. Выполните `harness mcp-config --client codex` и добавьте полученный TOML в настройки MCP Codex либо зарегистрируйте команду через `codex mcp add`.
3. Перезапустите Codex, если клиент ещё не перечитал настройки.
4. Пример: «Используй harness.run для изучения README в моей рабочей папке и дождись harness.status».

На текущем компьютере сервер `harness` уже зарегистрирован в `~/.codex/config.toml`; остальные MCP-записи сохранены, исходный файл скопирован в резервную копию с правами 0600.

Экспортируются только `harness.run`, `harness.status` и `harness.cancel`. Разрешения на запись и команды подтверждаются через CLI Harness. Управление ключами, опытом и квотами через MCP модели недоступно.

## Проверка

`npm run playtest:codex` проверяет настоящий маршрут MCP → Harness → Codex → fs.read. Скрипт использует вход текущего пользователя, расходует лимит аккаунта и работает в отдельной временной папке. В файл записывается случайное значение, которое модель обязана прочитать через инструмент и вернуть; сам запрос этого значения не содержит. Отчёт — [playtest-codex.json](playtest-codex.json).

Локальные тесты дополнительно проверяют список инструментов, отмену, обрыв потока до завершения, неправильные настройки, повреждённый JSONL и встречные RPC-запросы. Чистый запуск браузерного входа и нативный Windows остаются отдельными ручными проверками.
