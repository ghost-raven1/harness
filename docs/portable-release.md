# Готовые ZIP для запуска без установки Node.js

Portable-поставка содержит собранный Harness, закреплённый Node.js, конфигурации и production-зависимости для одной ОС и архитектуры. После распаковки не нужны системные Node.js/npm, установка библиотек или компиляция. Для обращения к облачным моделям по-прежнему требуется подключение; учебное демо работает без него.

## Выбор архива

Версия в имени берётся из `package.json`. Каждый ZIP сопровождается отдельным файлом `.zip.sha256`.

| Система             | Архив                               | Запуск                      |
| ------------------- | ----------------------------------- | --------------------------- |
| Linux x64           | `harness-<version>-linux-x64.zip`   | `sh ./start.sh`             |
| Windows x64         | `harness-<version>-windows-x64.zip` | `Запустить Harness.cmd`     |
| Mac с Apple Silicon | `harness-<version>-macos-arm64.zip` | `Запустить Harness.command` |
| Mac с Intel         | `harness-<version>-macos-x64.zip`   | `Запустить Harness.command` |

Распакуйте всю папку: файлы запуска используют лежащий рядом `runtime/node` или `runtime/node.exe`. Перенос одного launcher-файла без остальных файлов не поддерживается. На Linux и macOS передать аргументы можно через `sh ./start.sh --help` или `sh ./start.sh demo`. Исходный архив `harness-<version>-source.zip` предназначен для разработки и сохраняет прежнюю подготовку runtime, установку библиотек и сборку.

Готовый архив не содержит npm, компилятора, тестовых зависимостей, ключей и пользовательской истории. Нативные модули соответствуют целевой архитектуре; перенос установленного `node_modules` между разными ОС не используется.

Обычные задачи и настройки сохраняются в `~/.harness`, отдельно от папки распакованного приложения. Учебное демо использует собственную временную папку и удаляет её при выходе.

## Нативная сборка

Для публикуемой поставки используйте свежую рабочую копию выпускаемого коммита. Папка `config/` берётся из текущего дерева: упаковщик не заменяет локальные настройки исходной версией из Git. Перед упаковкой не добавляйте личные конфиги или ключи в эту копию. В CI для каждой платформы используется отдельный checkout.

На машине нужной ОС и архитектуры с закреплённым Node.js 24.21.0:

```sh
npm ci --include=dev --include=optional --no-audit --no-fund
npm run build
node scripts/portable-pack.mjs
node scripts/portable-check.mjs
```

Упаковщик копирует закреплённый Node.js с машины сборки и устанавливает production-зависимости из lockfile в отдельную временную папку. Сам runtime упаковщик не скачивает. Сеть нужна для получения npm-зависимостей и закреплённых LICENSE/NOTICE Codex; готовая поставка не выполняет эту подготовку при запуске. Архивы и суммы появляются в `releases/`. Упаковка и проверка ничего не публикуют.

## Что проверяется после распаковки

`portable-check.mjs` проверяет соответствующий текущей ОС архив в новой папке с пробелами и кириллицей. Дочерние процессы используют среду без системных Node.js/npm в `PATH`.

- Целостность состава и контрольные суммы.
- Запуск CLI и построение конфигурации MCP с runtime распакованной поставки.
- Загрузка нативного keyring без обращения к секретам или DBus и запуск встроенного Codex с `--version`.
- Учебный сценарий через настоящий runtime: ошибка, исправление, проверки, сравнение файлов и экспорт. API-ключи и облачная модель не используются.
- Завершение принадлежащих проверке исполнителей и очистка временных данных.

На время проверки в Node.js запрещены внешние TCP/HTTP/fetch-вызовы; локальный IPC учебного сервиса остаётся доступным.

Результаты: `releases/portable-check-<platform>-<arch>.json` и `.log`, подробный журнал упаковки — `releases/portable-pack-<platform>-<arch>.log`, где `<platform>` — `linux`, `windows` или `macos`. Эти проверки дополняют полный `npm run check`, исходную ZIP-поставку и PTY-сценарии; они не подменяют их.

## Матрица GitHub Actions

Задание `portable` в `.github/workflows/check.yml` собирает и проверяет четыре архива нативно:

| Runner           | ОС Node  | Архитектура |
| ---------------- | -------- | ----------- |
| `ubuntu-24.04`   | `linux`  | `x64`       |
| `windows-2025`   | `win32`  | `x64`       |
| `macos-15`       | `darwin` | `arm64`     |
| `macos-15-intel` | `darwin` | `x64`       |

Метки и архитектуры сверены с [официальной таблицей GitHub-hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners). Перед упаковкой задание дополнительно проверяет `process.platform`, `process.arch` и `RUNNER_ARCH`; несовпадение останавливает сборку. Эмуляция другой архитектуры не выдаётся за нативную проверку.

Матрица проверяет именно перечисленные среды. Поддержка других версий ОС или архитектур не подтверждается результатом соседнего задания.

После успешной проверки каждой платформы Actions сохраняет ZIP и SHA256 в артефакт `harness-portable-<platform>-<arch>`. Диагностика доступна отдельно в `harness-portable-ci-<platform>-<arch>`, в том числе после ошибки. Версия, commit, runtime и фактическая архитектура записываются в `environment.log`.

## Выпуск

Перед публикацией нужно дождаться всех заданий CI окончательного коммита в `main`, включая обычные проверки, Docker, PTY и четыре portable-задания. Успешная сборка одного архива не означает готовность остальных.

Из одного проверенного запуска Actions берутся четыре ZIP с суммами. Их версия должна совпадать с выпускаемым тегом, а commit — с проверенным `main`. Публикуются именно проверенные архивы; повторная локальная упаковка после CI создаёт другую поставку и требует новой проверки. Публикация карточки релиза выполняется отдельно: workflow имеет только `contents: read` и не создаёт теги или релизы.

Контрольные суммы помогают обнаружить повреждение файла, но не являются подписью издателя. Подпись приложения и нотариальное заверение macOS не заявлены.
