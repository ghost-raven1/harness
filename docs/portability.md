# Удобство и переносимость

Новый сценарий для новичка: [getting-started.md](getting-started.md). Рабочий стол запускает сервис сам, спрашивает ключ в скрытом поле и позволяет работать в одном окне.

## Реализованные сценарии

- Первый запуск: `init` создаёт отдельные конфиги проекта, `serve` находит их по текущей папке, `doctor` работает до запуска сервиса.
- Ежедневная работа: выбор workspace независимо от профиля, повторяемое меню, содержательные списки запусков и опыта, параметры вывода без TTY.
- Интеграция: `mcp-config` печатает готовую настройку OpenCode с фактическими путями текущей системы.
- IPC: Unix-сокет на macOS/Linux, именованный канал с проверкой локального токена на Windows. Длинные Unix-пути используют отдельный короткий каталог сокетов текущего пользователя.
- Файлы: проверка границ workspace учитывает разделитель ОС; политика путей использует нормализованные разделители. Windows сохраняет fsync файлов, без неподдерживаемого fsync каталогов.
- Процессы: буквальные аргументы без неявного shell; окружение и остановка дерева учитывают ОС.
- Проверка: весь набор на Node 24.21.0 локально и в Linux-контейнере; матрица CI для macOS, Ubuntu и Windows. Непроверенные платформы обозначаются явно.

Конфигурация, политики и версии опыта активных запусков сохраняются. В исходной поставке файлы запуска подготавливают Node.js 24.21.0 внутри `.tools`, не меняя системный runtime. [Готовые ZIP](portable-release.md) уже содержат runtime и production-зависимости; их запуск не требует установки Node.js или npm.

## Платформы и результаты проверки

Обычная матрица CI проверяет Ubuntu, macOS и Windows. Отдельные задания готовой поставки используют `ubuntu-24.04` x64, `windows-2025` x64, `macos-15` arm64 и `macos-15-intel` x64. ZIP каждой платформы проверяется на её нативном runner после распаковки. [Состав проверок и артефактов](portable-release.md) отделяет запуск готового приложения от установки исходной поставки.

Результат относится к конкретному коммиту и среде: актуальные логи находятся в GitHub Actions, а опубликованные архивы — в карточке соответствующего выпуска. Локальные тесты не подтверждают нативную работу другой ОС. Облачные модели и вход в аккаунт Codex не вызываются при проверке portable ZIP; она использует учебного провайдера без сети.

Linux проверяется воспроизводимо:

```bash
docker build -f Dockerfile.test -t modular-harness-test:local .
docker run --rm modular-harness-test:local
```

Образ Node закреплён digest. Контейнер не получает ключи или состояние пользователя и не публикует порты. Это образ для проверки, а не развёртывание сервиса. Файл `.github/workflows/check.yml` запускает проверки после push и pull request; результат CI нельзя считать полученным до завершения соответствующего запуска.

## Что различается между ОС

- macOS/Linux используют Unix-сокет с правами 0600 и каталогом 0700. Короткие прежние адреса сохранены; длинные пути получают адрес в личном временном каталоге.
- Windows использует `\\.\pipe\harness-…`. Каталог состояния защищается ACL текущего пользователя через штатный Windows PowerShell. Каждый запрос проверяет случайный локальный токен; токен не передаётся модели и не экспортируется MCP.
- Содержимое журналов и снимков синхронизируется через fsync на всех ОС. На Windows пропускается неподдерживаемый fsync каталога; устойчивость к отключению питания не проверена.
- Windows-пути проверяются с учётом дисков, UNC и обратного слеша. Запреты файлов нормализуют разделители и учитывают регистр Windows.
- Отмена использует группу процессов POSIX или штатный `taskkill /T /F` на Windows. Требуются SystemRoot и Windows PowerShell; Linux/macOS не зависят от них.
- Процессы выполняют буквальный argv. Оболочка запускается только как явно запрошенная программа, которая отдельно проходит политику разрешений.

Проверка вариантов `path.win32`, адреса именованного канала и Windows-окружения на macOS/Linux не заменяет запуск в Windows. Windows CI должен подтвердить ACL, каналы, PowerShell и taskkill до объявления полной поддержки.

## Пройденные пользовательские сценарии

- Создание нового проекта в пути с пробелами и кириллицей.
- Повторный `init` с сохранением существующих авторских файлов.
- Поиск конфигурации из вложенной папки.
- Диагностика до запуска сервиса и после него.
- Мастер локального API без ключа; успешный запуск из меню.
- Выбор workspace при явно указанном профиле.
- Возврат в меню после пустого списка, выполненной задачи и просмотра опыта.
- В расширенных командах отмена ввода возвращает код 130. В рабочем столе Esc возвращает в меню, выход с активными задачами требует решения.
- Приём задачи из stdin, отказ при пустом вводе и построчный JSON.
- Формирование готовой конфигурации OpenCode с фактическими путями.

В маленьком терминале карточки переносят строки без потери данных. Для копирования структурированных значений используйте `--json`; логотип и ANSI в этот поток не попадают.
