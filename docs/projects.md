# Проекты: от цели до принятого результата

Проект сохраняет цель, принятый план, этапы и доказательства проверок. Рабочая папка остаётся обычной папкой на вашем компьютере. Для короткого вопроса по-прежнему подходит «Новая задача»; для работы с несколькими этапами откройте «Проекты».

## Первый проект

1. В настройках выберите папку и модель. Затем откройте **Проекты → Новый проект**.
2. Опишите желаемый результат. Enter добавляет строку, Ctrl+S отправляет описание, Esc сохраняет черновик.
3. Harness изучит папку и предложит план. На этом шаге доступны только инструменты чтения.
4. Откройте вкладку **План**. Проверьте роли, зависимости этапов, ожидаемый результат, точные команды с аргументами и ручные проверки.
5. Нажмите Enter для действий. Можно **попросить изменить план** обычными словами или изменить **предел исправлений**. Каждое изменение создаёт новую версию, которую нужно принять.
6. Выберите **Принять план и начать**. Harness сначала проверит исходное состояние, выполнит этапы и проверит их результаты.
7. Если нужна ручная проверка, выполните показанные действия и выберите **Проверить результат вручную**. Укажите, что именно проверили и что получилось.
8. После итоговой проверки выберите **Принять результат**. Успешный ответ модели сам по себе не завершает приёмку проекта.

Список, карточка проекта, план, проверки и журнал обновляются при работе другого окна. Tab переключает разделы, ↑↓ и PgUp/PgDn прокручивают текст, Esc возвращает назад. Журнал, публичные пояснения модели и полный ответ конкретного этапа открываются через **Журнал, мысли и ответ этапа**. В карточке проекта хранится ограниченное окно последних загруженных событий; полные события доступны страницами через `projects show --cursor`.

## Пауза, ошибки и изменения файлов

- **Приостановить** сохраняет состояние и ждёт завершения текущих операций. **Продолжить** проверяет, не изменились ли файлы за время паузы.
- При внешних изменениях просмотрите состав и подтвердите продолжение. Старые проверки не доказывают корректность нового состояния: для приёмки нужна повторная проверка.
- Если исходные проверки не проходят, выберите **Включить исправление исходных ошибок в план**, затем примите новую версию плана. Harness не считает старую ошибку успешно выполненной работой.
- При исчерпании исправлений проект ждёт решения. По умолчанию разрешены две попытки исправления; предел меняется в плане.
- При неизвестном результате прерванной операции откройте **Проверить прерванную операцию**. Проверьте фактический эффект и зафиксируйте исход. Такая операция автоматически не повторяется.
- Сообщение работающему этапу передаётся через **Уточнить работающему этапу**. Оно адресовано конкретному этапу; Harness не переносит его автоматически в следующий этап.
- После аварийного завершения работа автоматически не продолжается. Откройте сохранённый проект, проверьте его состояние и продолжите явно.

Окно-владелец при выходе закрывает сервис и приостанавливает проекты. Подключённое второе окно только отключается. Для работы в фоне оставьте отдельное окно `serve`.

## Архив и удаление

**Убрать в архив** скрывает проект из основного списка; **Показать архив** позволяет открыть и вернуть его. **Удалить навсегда** показывает предпросмотр связанных задач, бесед и артефактов. Подтверждение относится к этому составу и перестаёт действовать при изменении данных в другом окне. Каскад также удаляет историю проекта и его черновики. Рабочие файлы проекта остаются на диске.

Управляемые проектом задачи открывают карточку проекта для паузы, продолжения, сообщений и удаления. Это сохраняет связи плана и проверок. Проектные команды не экспортируются модели через MCP.

## Команды для скриптов

Команды подключаются к работающему локальному сервису. Перед `projects` добавляйте `npm start --` либо `node dist/interfaces/cli.js`. Флаг `--json` включает машинный ответ.

```bash
npm start -- --json projects create "Страница ошибок" "Добавить понятную страницу ошибки и проверить её" --workspace /путь/к/папке --key create-001
npm start -- --json projects show PROJECT_ID
npm start -- --json projects plan PROJECT_ID --revision 1 --key plan-001
```

Ревизию всегда берите из актуального `show`. При повторе запроса после потери связи сохраняйте **весь исходный payload, прежние `--revision` и `--key`**. Для нового решения используйте новый ключ. Версия плана (`--plan-version`) и отпечаток проверенных файлов (`--result-revision`) независимы от ревизии карточки.

| Команда                                            | Дополнительные параметры                                                            |
| -------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `projects list`                                    | `--query`, `--page` с нуля, `--archived`                                            |
| `projects show PROJECT_ID`                         | `--cursor` для следующей страницы событий                                           |
| `projects create TITLE GOAL`                       | `--workspace`, `--profile`, `--key`                                                 |
| `projects plan PROJECT_ID`                         | `--revision`, `--key`, необязательные `--feedback` и `--goal`                       |
| `projects edit PROJECT_ID`                         | `--revision`, `--key`, `--file plan.json`                                           |
| `projects accept-plan PROJECT_ID`                  | `--revision`, `--key`, `--plan-version`                                             |
| `projects pause PROJECT_ID`                        | `--revision`, `--key`                                                               |
| `projects resume PROJECT_ID`                       | `--revision`, `--key`, `--accept-changes` после просмотра изменений                 |
| `projects cancel PROJECT_ID`                       | `--revision`, `--key`                                                               |
| `projects message PROJECT_ID STAGE_ID TEXT`        | `--revision`, `--key`                                                               |
| `projects manual-check PROJECT_ID STAGE_ID`        | `--revision`, `--key`, `--result-revision`, `--outcome passed\|failed`, `--comment` |
| `projects recheck PROJECT_ID`                      | `--revision`, `--key`                                                               |
| `projects accept PROJECT_ID`                       | `--revision`, `--key`, `--result-revision`                                          |
| `projects archive PROJECT_ID`                      | `--revision`, `--key`, `--restore` для возврата                                     |
| `projects purge-preview PROJECT_ID`                | Показывает состав и токен удаления                                                  |
| `projects purge PROJECT_ID`                        | `--revision`, `--key`, `--preview-token`                                            |
| `projects resolve PROJECT_ID RUN_ID INVOCATION_ID` | `--revision`, `--key`, `--result`, `--outcome succeeded\|failed`                    |

Расширенное редактирование через JSON требует объект с `stages`, `maxCorrections`, `fixBaselineFailures`, без `version`. Формат проверяется по `src/projects/schema.ts`; роли и инструменты должны существовать в конфигурации. В обычном интерфейсе знание JSON не требуется.

## Границы для разработчиков

`projects/schema.ts` определяет контракты, `ProjectService` проверяет решения человека, координатор управляет этапами через внутренний порт runtime. Прикладной обработчик `application/commands/projects.ts` использует доменные схемы; CLI и IPC используют их же через типизированный реестр. Отдельные файлы в `interfaces/guided/project-work/` отвечают за представление, план, проверки, действия, черновики и навигацию.

Перед мутацией проверяются ревизия и ключ. Принятие плана дополнительно закрепляет его версию; приёмка — отпечаток файлов. Подтверждение на экране содержит неизменный снимок, а опрос сервиса проверяет его актуальность. Черновики используют `purpose`, `projectId`, `stageId`; отправленный черновик также сохраняет `expectedProjectRevision`. Очередь проекта берётся перед очередью файлов состояния, как при каскадном удалении.

Состояние проектов хранится отдельно в `project-records`. Переписки этапов остаются в обычных задачах. Старый каталог `projects` с настройками подключений не переносится и не переименовывается.
